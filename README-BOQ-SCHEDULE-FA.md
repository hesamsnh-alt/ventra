# زمان‌بندی از BOQ و جدول انجام کارها — ۷ اکتبر ۲۰۲۶

این بسته قابلیت زمان‌بندی را اضافه می‌کند. ZIP قبلی workspace-records دارای ایراد بود؛ فایل 20261007_workspace_records.sql آن بسته را اجرا نکنید. این قابلیت به آن فایل وابسته نیست.

## نصب ساده
۱. از پوشهٔ ventra یک کپی پشتیبان بگیرید و سرور توسعه را با کلیدهای Ctrl+C متوقف کنید.
۲. محتویات پوشهٔ ventra داخل ZIP را روی پوشهٔ ventra پروژه کپی کنید؛ مسیرهای src و supabase باید روی همان پوشه‌های موجود قرار بگیرند. فایل محیطی یا کلیدها در این بسته نیستند.
۳. در داشبورد Supabase همان پروژه، SQL Editor → New query را باز کنید.
۴. ابتدا تمام محتوای supabase/migrations/20261006_project_control.sql را اجرا کنید (اگر قبلاً اجرا شده، مجدداً قابل اجراست).
۵. سپس تمام محتوای supabase/migrations/20261007_boq_schedule_plans.sql را در یک Query جدا اجرا کنید.
۶. در پوشهٔ ventra، npm run build و بعد npm run dev را اجرا کنید. در این محیط build با Webpack و Next 16.2.10 بررسی شد؛ package پروژه 16.3.8 باقی مانده است.

این SQLها از اینجا روی دیتابیس واقعی شما اجرا نشده‌اند. کلید خصوصی را در چت نفرستید.

## استفاده داخل برنامه
۱. BOQ پروژه را باز کنید و مقدار، واحد و شرح ردیف‌ها را بررسی کنید؛ همان BOQ ذخیره‌شده در این مرورگر مبناست.
۲. تب Schedule / Timeline → Load / reload project BOQ.
۳. تاریخ شروع پروژه/قرارداد، ساعات شیفت، استراحت، ضریب ساعت مفید، روزهای هفته و تعطیلات را تنظیم کنید. تاریخ پروژه در صورت وجود پیشنهاد می‌شود؛ تاریخ قرارداد به‌طور خودکار استخراج نمی‌شود.
۴. برای هر آیتم بخش کار، روش اجرا، تعداد تیم کامل، ظرفیت ساعتی و ترتیب اجرا را بررسی کنید. نوار روش‌ها مدت هر روش دارای نرخ را نشان می‌دهد. نرخ دلخواه هر روش با تغییر روش در همان پیش‌نویس حفظ می‌شود.
۵. زمان انتظار لازم بعد از بتن، ملات، عایق و کاشی باید صریح وارد شود. این مقدار به دستور مهندس، محصول، رطوبت و نوع کار وابسته است؛ صفر را فقط آگاهانه وارد کنید. سیستم مجوز بارگذاری سازه صادر نمی‌کند.
۶. آیتم نامرتبط را فقط با ثبت دلیل کنار بگذارید. موارد ناشناخته، مقدار نامعتبر یا نرخ خالی مانع محاسبه می‌شوند. بتن با مترمربع قابل محاسبه نیست؛ حجم صحیح مترمکعب را در BOQ اصلاح کنید.
۷. تیک بررسی فرض‌ها → Calculate dates and preview. خروجی را ببینید؛ سپس Save new shared baseline. بدون نصب SQL، پیش‌نمایش و خروجی JSON قابل استفاده‌اند ولی ذخیرهٔ مشترک فعال نیست.
۸. در جدول هر فعالیت تیک Done یا درصد میانی ثبت کنید. بازکردن تیک درصد را به صفر برمی‌گرداند. برای اصلاح جزئی از فیلد درصد استفاده کنید.
۹. Refresh shared plan برای دیدن آخرین تغییرات دیگر دستگاه‌ها. این نسخه همگام‌سازی لحظه‌ای push ندارد؛ تداخل ویرایش با شمارهٔ نسخه رد می‌شود تا دادهٔ همکار بی‌صدا بازنویسی نشود.

## مفهوم پیشرفت و هشدار
- پیشرفت برنامه بر اساس سهم «مقدار ÷ ظرفیت ساعتی هر تیم» وزن دارد؛ فقط شمارش تیک‌ها نیست. این شاخص نفرساعت دقیق، پیشرفت فیزیکی تأییدشده یا مجوز دریافت پول نیست.
- درصد کلی پروژه همچنان با تأیید کاربر ثبت می‌شود. درصد برنامهٔ BOQ جدا در کنار آن نشان داده می‌شود؛ میانگین نامعتبر Tasks/Reports/Schedule قبلی حذف شده است.
- عقب‌افتاده: پیشرفت ثبت‌شده بیش از ۵ واحد درصد کمتر از پیشرفت خطی تا پایان روزهای کاری گذشته است.
- سررسیدگذشته: امروز بعد از پایان برنامه است و پیشرفت کمتر از ۱۰۰٪ است. تاریخ امروز بر مبنای دبی است.
- قرمز بر اساس دادهٔ ثبت‌شده است؛ بدون گزارش جدید، برنامه وضعیت واقعی کارگاه را نمی‌داند. برچسب «No progress report yet» نمایش داده می‌شود.
- هر برنامه تاریخ مبنای ثابت دارد. تأخیر با جابه‌جایی خودکار تاریخ‌ها پنهان نمی‌شود. تولید برنامهٔ جدید سابقه را نگه می‌دارد ولی درصدهای برنامهٔ تازه صفر است.
- آیتم‌های حذف‌شده از دامنه کنار درصد نمایش داده می‌شوند؛ ۱۰۰٪ این جدول لزوماً پایان کل پروژه نیست.

## دامنه و ترتیب اجرا
بخش‌های تجهیز کارگاه، تخریب، خاک‌برداری، خاک‌ریزی، قالب، آرماتور، بتن، بنایی، برق، لوله‌کشی، تهویه، اطفا، سقف و عایق، پنجره، پلاستر، عایق رطوبتی، کف‌سازی، سقف کاذب، کاشی، کفپوش، رنگ، نجاری، نصب نهایی، محوطه و تست وجود دارند. واحد از BOQ می‌آید؛ نرخ هر روش باید دقیقاً در همان واحد باشد.

الگوی ترتیب اولیه یک جبههٔ کاری محافظه‌کارانه با پایان‌به‌شروع است. برنامهٔ چندطبقه/چندزون، هم‌پوشانی تیم‌ها، مسیر بحرانی و تسطیح منابع در این نسخه پیاده نشده‌اند. ترتیب را برای پروژه تأیید کنید؛ مثالاً ترتیب خاک‌ریزی یا عایق با نوع سازه تغییر می‌کند. اقلام خرید صرف و مبلغ مقطوع باید به عملیات اجرایی مناسب تبدیل یا با دلیل کنار گذاشته شوند.

## نرخ‌ها و منابع
نرخ قطعی عمومی برای تمام ساختمان‌ها وجود ندارد. سه نمونهٔ مطالعه‌شده برای شروع پیشنهاد می‌شوند؛ نرخ بقیهٔ رشته‌ها باید با خروجی کارگاه یا پیمانکار تکمیل شود. «Enter rate» یعنی آن روش هنوز برآورد زمان ندارد، نه اینکه مدت آن صفر است.

- پلاستر دستی: ۲٫۸ مترمربع/ساعت؛ مطالعهٔ Makerere، Mbaine (2021)، Kampala: https://dissertations.mak.ac.ug/handle/20.500.12281/9607
- بتن پمپی: مطالعهٔ Petra (2010) خروجی ۷٫۶۹ تا ۱۱٫۷۲ مترمکعب/ساعت در ترازهای بررسی‌شده؛ پیشنهاد اولیهٔ برنامه ۸ است. باکت/جرثقیل در همان منبع ۶٫۲۸ تا ۷٫۸۶؛ پیشنهاد ۶٫۳ است. نرخ دستی از این اعداد استنتاج نشده: https://repository.petra.ac.id/id/eprint/4896/
- کاشی گرانیتی: TELSINAS 8(1) (2025)، ۷٫۳۵ تا ۸٫۰۸ مترمربع در روز ۸ساعته. نرخ اولیهٔ گرد‌شده ۱ مترمربع/ساعت است و برای هر نوع کاشی تضمین نمی‌شود: https://journal.undiknas.ac.id/index.php/teknik/article/download/6156/1715

منابع خارج اماراتند و اندازه/ترکیب تیم، روش و تعریف زمان آن‌ها الزاماً با پروژهٔ شما برابر نیست. تبدیل به ساعت مفید و الگوی ترتیب اجرا فرض‌های برنامه‌اند. ساعات استراحت/اتلاف را هنگام استفاده از نرخ روزانهٔ از قبل تعدیل‌شده دوباره کسر نکنید.

## وضعیت آزمون
هشت آزمون موفق: روزهای کاری، تعطیلات، فاصلهٔ تقویمی، تفاوت روش، واحد نادرست بتن، آیتم ناشناخته، هشدار تأخیر و وزن پیشرفت؛ همچنین اجرای دوبارهٔ SQL، مالک/سرپرست/بیننده/غریبه/ناشناس، منع نوشتن مستقیم، ثبت رویداد و تعارض ویرایش روی PostgreSQL محلی PGlite آزمایش شد. Build با Webpack و lint فایل‌های جدید موفق بودند. اجرای زندهٔ دو حساب روی Supabase شما و تست ظاهری مرورگر ادعا نمی‌شود.

رکوردهای قبلی مرورگر و جدول‌های قدیمی حذف یا خودکار مهاجرت نمی‌شوند. برنامه‌های جدید در جدول‌های مستقل ventra_schedule_plans و ventra_schedule_events هستند. اعضا از /project-control/PROJECT_ID هم به جدول دسترسی دارند؛ viewer فقط مشاهده می‌کند.
